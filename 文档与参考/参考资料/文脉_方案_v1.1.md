## 一、为什么改定位（问题诊断）

上一版方案叫「文献综述助手」，能力是"读懂文献、找出缺口"。它有一个真实的短板：

| 它产出 | 学生真正需要的 |
|---|---|
| 一段"综述初稿"文字 | 一个**能直接粘进论文的 Word 文件** |
| 输入是"一堆散装 PDF" | 学生真实入口是**知网导出的题录** |
| "研究缺口分析" | 导师不看你有没有找到缺口，**只看你论文写得规不规范** |
| "引用溯源"很酷 | 学生要的是**参考文献表自动排好** |

**一句话：它帮你"读懂"，但不帮你"交得出去"。**

新定位做了两件事：

1. **把出口做实用**——输出可直接使用的 Word 稿件，参考文献自动按 **GB/T 7714**（国内学位论文参考文献格式国标）排好。
2. **把可信度做硬**——生成之后**自动自检**：引用是否真实存在、编号顺序对不对、格式合不合规、有没有该引没引。

**第 2 件事同时解决了两个问题**：
- 回应"这不就是 AI 代写吗"的质疑——系统自己会指出自己哪里不可靠；
- **把评测指标做成可自动判定的硬数字**——"引用格式合规率""引用可核实率"是能算出来的，比"综述写得好不好"这种主观打分强得多。

## 二、它到底帮学生做什么（五步）

```
① 导入文献：上传 PDF，或直接粘贴知网/CNKI 导出的题录
        ↓
② 自动建卡：每篇生成一张文献卡片（问题·方法·数据·指标·局限）
        ↓
③ 拼成矩阵：所有卡片拼成一张对比表，看清谁强谁弱、谁在同一赛道
        ↓
④ 起草综述：按主题分组写"研究现状"，正文句尾带 [1][2] 引用角标
        ↓
⑤ 自检与导出：检查每条引用是否真实、格式是否合规 → 生成参考文献表
        → 导出 Word，打开即可用
```

## 三、七个核心功能（★ 为差异化重点）

| 编号 | 功能 | 干什么 | 为什么必须要大模型 |
|---|---|---|---|
| F1 | **题录智能解析** | 粘贴知网/CNKI 导出的题录文本，自动拆成结构化字段 | 各库导出格式五花八门，规则匹配维护不过来 |
| F2 | **文献卡片提取 ★** | 每篇 PDF 自动生成卡片：解决什么问题、用什么方法、用什么数据、结果多少、局限在哪 | 这一步是"读懂"，只有模型能做 |
| F3 | **对比矩阵** | 卡片拼成大表，看出强弱与赛道分布，可导出 Excel | 需要理解、对齐、归纳 |
| F4 | **综述初稿起草** | 按主题分组写"研究现状"章节，**每句带引用角标** | 学术写作必需 |
| F5 | **引用真实性自检 ★** | 逐条检查：这个 `[3]` 指的文献真的存在吗？论断真在原文里吗？ | 需要回原文比对，防止编造引用 |
| F6 | **格式合规自检 ★** | 编号是否连续、正文与文末是否一一对应、有没有漏引、是否重复著录 | 需要同时理解正文与文末 |
| F7 | **参考文献表生成** | 自动生成 **GB/T 7714** 格式参考文献表，一键导出 Word | 格式琐碎、规则繁多，人最容易出错 |

**★ 的 F5、F6 是拉开差距的地方。** 多数队伍做的是"帮你读文献"，我们做的是"帮你把论文写合规"。

## 四、自检到底检查什么（这是最实用的一块）

自检报告是一份**清单**，每条都告诉你位置、问题、怎么改：

| 检查项 | 具体检查内容 | 输出示例 |
|---|---|---|
| **引用真实性** | 正文每个角标对应的文献是否真实存在于参考文献表 | "第 3 段 `[7]` 在参考文献表中不存在" |
| **论断有据** | 每句话的论断能否在对应文献原文找到依据 | "该论断在 `[4]` 原文中未找到支撑" |
| **编号顺序** | 角标是否按出现顺序编号、是否连续、有无跳号 | "角标顺序为 1,2,4,3 —— 第 4 处与第 3 处顺序颠倒" |
| **正文文末对应** | 正文引用与文末条目是否一一对应 | "`[9]` 在正文中从未出现" |
| **该引未引** | 哪些论断明显需要引用但没引 | "第 5 段的方法论断建议引用 `[2]`" |
| **格式合规** | 是否符合 GB/T 7714（作者、题名、文献类型标识、出版项、页码） | "`[6]` 缺少文献类型标识 `[J]`" |
| **重复著录** | 同一文献是否被著录两次、编号是否重复 | "`[3]` 与 `[11]` 为同一篇文献" |

**输出**：一份自检报告（可导出），每条问题带位置定位与修改建议。

## 五、技术方案

对应阿里官方 4 条路径，本方案选**路径 C（RAG + 微调）**为主，并入路径 A 的 Agent 能力。
**下表"实施状态"列为实测结论，未实施的能力如实标注，不在任何材料中声称已完成。**

| 环节 | 技术 | 对应官方路径 | 实施状态 |
|---|---|---|---|
| 综述检索、论断比对、格式判断 | **RAG**（检索增强生成） | A / C | ✅ **已实施**（详见 5.1） |
| 自检全流程编排、修改建议生成 | **Agent 工具调用** | A | ✅ **已实施**（详见 5.2） |
| 文献卡片结构化抽取、引用格式规范化 | **LoRA 微调千问小模型** | C | ⚠️ **未实施**（详见 5.3） |
| 批量处理 30–50 篇文献 | **工作流编排** | 加分 | ✅ 已实施（分阶段命令 + 断点跳过） |
| 模型调用、向量检索 | **阿里云百炼：通义千问 + text-embedding-v3** | 满足"必须使用阿里云产品或平台" | ✅ **已实施** |
| 模型训练、云服务器 | PAI + ECS | — | ⚠️ 受算力与部署条件限制未使用 |

### 5.1 RAG 的实施细节（已落地）

文脉的 RAG 由"检索"与"生成"两部分组成，**检索是后补上的关键环节**：

| 环节 | 实现 | 说明 |
|---|---|---|
| **切块** | `split_for_index()` 把每篇论文全文切成语义完整的段落（≤800 字/块，约 90 块/篇） | **覆盖全文 100%**（实测 101%–117%，含摘要/方法/结论的重复纳入） |
| **向量化** | **阿里云百炼 `text-embedding-v3`**（1024 维），带磁盘缓存 | 首次建索引约 46 秒（494 块），二次运行读缓存 |
| **检索** | 多查询并行：整句 + 关键词 + 子句 + **英文检索词**，取并集排序 | 中文论断检索英文论文必需——实测不加英文扩展会把真实引用误判为"无支撑" |
| **生成/判定** | 检索到的原文段落交模型判断论断是否成立 | 输出"有支撑/存疑/无支撑"+ 依据所在片段 |

**为什么要用真正的 embedding 模型**：早期版本用字符 n-gram 相似度，它只反映**字面重叠**而非语义。
实测对比同一问题：字符 n-gram 最高相似度 0.30 且检索结果**均不含**关键词；
换成 text-embedding-v3 后相似度 **0.72** 且**全部命中**含证据的段落。
这一改动直接决定了引用自检的准确率。

**判别能力实测**（这是本项目最硬的指标）：

| 测试 | 结果 |
|---|---|
| 真实引用（4 条论断） | 判"有支撑"，理由引用具体片段，**支持率 1.00** |
| 故意编造的引用（3 条） | **全部判"无支撑"，支持率 0.00** |
| 两组对比 | 0.00 vs 1.00，证明判别有效而非"永远通过" |

### 5.2 Agent 工具调用的实施细节（已落地）

**与"固定流水线"的本质区别：谁来决定检查什么。**

| | 固定流水线（未采用） | 本项目的 Agent（已采用） |
|---|---|---|
| 顺序 | 代码写死 | **模型自己判断** |
| 变通 | 不会 | 发现问题后**自主决定下一步查什么** |
| 过程 | 不透明 | 输出完整**工具调用轨迹**，每步可溯源 |

**9 个工具**（均为已有能力的原子封装）：
`list_sentences`（读全稿）、`get_sentence`、`reference_by_index`、
`check_citation_existence`、`check_ordering`、`check_format`、
`find_evidence`（回原文检索）、`check_claim_support`（RAG 核对）、`generate_report`。

**实测运行记录**：17 步自主完成，使用 **8 种工具**，无人工干预。
Agent 实际抓出的问题举例：

- 称某文献"推理效率提升 10 倍"，而**原文未提及该数字**（编造量化表述）；
- 用 2017 年的方法论文支撑"对现代鲁棒性场景的批评"（**文献与论断错配**）；
- 称某文献在四个数据集"均达 SOTA"，**原文只验证了机制**（结论夸大）。

**可验证性设计**：Agent 每一步的结论旁都有「查看它检索到的原文」按钮，
用户可自行核对依据，而不是盲目信任——这是"可验证的信任"。

### 5.3 微调路径与实施说明（未实施，如实说明）

**原计划**：采用 **LoRA 微调千问小模型**处理文献卡片抽取与引用格式规范化。
这两类任务字段固定、格式高度一致，微调可显著降低延迟与成本，并减少字段遗漏与格式漂移。

**未实施的原因**：经核实，阿里云学生算力专区**未提供 GPU 机型**（专区在售为云服务器、
轻量应用服务器等 CPU 实例），微调所需算力无法获取。

**微调本可解决的问题**（实测确实存在）：
用 6 篇文献的卡片做实测，发现模型输出存在——① 语言不统一（部分字段输出英文原文而非中文概括）；
② 摘抄而非概括（"可借鉴点"输出原文句子截断）；③ 字段偶有格式漂移。**这三类正是微调最擅长的**。

**等效替代方案**（已实施）：为保证输出稳定性，改用三重约束——

1. **严格 JSON Schema** 约束输出结构，解析失败自动重试；
2. **本地质量闸门**：过滤语言不一致、超长摘抄、章节标题残留等脏输出；
3. **回原文核对**：由 RAG 检索与模型判定共同验证内容真实性。

**实测效果**：6 篇文献的卡片字段完整率达 100%（研究问题/方法/数据/指标/可借鉴点）。

**遗留代价**：其中"局限"字段缺失 3/6——原文本身未自述局限、或经语言过滤后被丢弃。

**后续工作**：获得 GPU 资源后，将以本次积累的卡片数据作为标注种子实施 LoRA 微调，
目标为降低单篇成本，并提升"局限"等弱字段的抽取率。

**为什么这项诚实声明反而重要**：微调解决的是"**听话**"（输出规范），不是"**聪明**"（内容正确）。
本项目最核心的能力——引用真实性核查——**微调帮不上忙**，必须靠 RAG 检索与自检实现。
把资源投在检索与自检上，是本项目在算力受限下的理性选择。

## 六、边界（不做什么）—— 也是学术诚信声明

- ❌ **不做代写**：系统生成的是**骨架 + 引用**，观点判断与最终定稿由学生完成
- ❌ **不做降重**：不提供任何规避查重的功能
- ❌ **不做通用文献搜索引擎**：比不过知网、谷歌学术
- ❌ **不做全自动写完整篇论文**：不可信，也不应该做
- ✅ **只做一个研究方向、30–50 篇文献**：赛题强调的"小而美"

**产品定位声明**：文脉是**写作与校对的助手**，不是写作的替代者。所有 AI 生成内容在界面上明确标注，并要求用户确认后方可导出。

## 七、怎么证明它有效（评测方案）

赛题必需提交"在验证集上的评测结果"。本方案的每一项都有可复现的数字与对比基线。

> ⚠️ **本表是立项时的目标值，不是实测结果。** 实际交付的评测数字与复现方式见
> 《`文档与参考/交付文档/02_验证集评测结果.md`》。两者口径不同，**请勿把本表的
> "目标"当成已达成的指标**——其中"微调有效性"一项因学生专区无 GPU 机型**未实施**，
> 样本量也未达到本表设想（实测为 6 篇论文 + 4 类注入错误）。

| 评测项 | 怎么测 | 样本量 | 目标 |
|---|---|---|---|
| 检索命中率 | 出问题看能否找到该找的论文 | 100 组 | 0.55 → **≥ 0.90** |
| 卡片抽取准确率 | 人工逐字段核对 | 50 篇 | 72% → **≥ 92%** |
| 微调有效性 | 同一任务：纯提示词 vs 微调模型 | 50 篇 | 提升 ≥ 15 个百分点，成本减半　⚠️ **因无 GPU 未实施，本轮不提交该项结果** |
| **引用格式合规率 ★** | 生成的参考文献表逐条比对 GB/T 7714 | 200 条 | **≥ 95%** |
| **引用可核实率 ★** | 逐条核对引用是否真实、论断是否有原文依据 | 150 条 | **≥ 95%** |
| **自检查全率 / 查准率 ★** | 人工埋入已知错误（错编号、假引用、缺标识、重复著录），看能否查出 | 各 50 处 | 查全 **≥ 0.90**／查准 **≥ 0.90** |
| 缺口识别覆盖率 | 用真实论文引言中作者自述的缺口作标准答案 | 20 篇 | ≥ 0.75，胡说率 ≤ 0.10 |
| 端到端任务成功率 | 从导入到导出 Word 全程无人工干预完成 | 50 次 | **≥ 0.90** |
| 响应速度 / 成本 | 30 篇从导入到出稿，全程计时计费 | — | p95 ≤ 120 秒 ／ 单次 ≤ 1.5 元 |

**方法说明**：自检能力采用**埋错测试法**——人为在文本中植入已知错误，验证系统是否检出，这样指标客观、可复现、无法造假。
